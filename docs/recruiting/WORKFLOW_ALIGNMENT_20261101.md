# 运营工作流调整稿

状态：已按确认范围实施；验证记录见末节。

## 1. 统一业务任务

页面只显示一条任务链：已接收 → 解析材料 → 整理资料 → 已入库 → 匹配中 → 匹配完成。

解析失败、待补资料、匹配失败分别停在对应阶段；重试只重做失败阶段。匹配失败保留已入库资料；无合适结果属于匹配完成；资料更新属于需重新匹配。岗位批量导入保留子项明细。

列表字段：名称、类型、渠道、时间、状态、详情。类型使用下拉筛选：全部、人找岗、岗找人。底层允许不同 worker 分工，但不能把内部队列当作用户的业务分类。

## 2. 手动匹配

按钮改为开始匹配，留在当前页显示执行过程和结果，不弹出全局队列。复用后端异步执行、幂等和缓存，避免长推理占住同步请求。指定人岗组合是本地重建时增加的 PAIR 入口，先从运营菜单移除；单对评估仍是内部基础能力。

## 3. 匹配结果内生成文案

删除独立问候与发布草稿入口。结果默认勾选前五，提供全选、取消、筛选和加载更多。总共十个，默认显示并选中前五个；加载更多显示剩余五个。

将已选对象的职业资料、JD、公司上下文和评分依据一起提交生成服务。生成文案与对象选择和资料版本关联保存，支持编辑、重新读取和一键复制；生成完成默认尝试写入剪贴板，被浏览器拒绝时明确提示。没有自动发送、发布或联系状态修改。

## 4. 邮件与设置

邮件详情顶部固定一个紧凑返回按钮。全部详情和预览弹窗统一右上角 X，保留 Escape 和可访问名称。邮箱配置迁入正式设置区。

官方 Twenty 已有账号配置和邮件同步服务。泛函旧实现依赖 Twenty 收信事件，再由定制代码使用 IMAP 补取原文与附件。当前本地实现复用官方 IMAP 连接，开启后约每分钟检查新 UID，完整归档后自动进入招聘 intake。GreenMail 只是本地测试邮箱。

当前附件使用 Twenty 原生文件权限和本地存储。若增加桶，优先复用官方 S3 兼容驱动，不在邮件模块维护第二套存储权限。本地已使用独立 MinIO 桶，线上继续使用原 InstaCloud 存储。

## 本地验收

- 队列改为 processing-tasks：同一材料任务串起解析和匹配，类型下拉筛选；整体 state 不再因资料已入库而提前完成。
- 手动匹配留在当前页显示进度和结果；指定人岗组合从运营菜单移除；没有在统一队列新增材料行。
- 匹配服务返回最多十条，默认选择前五；展开、全选、生成、保存及自动复制均有回归覆盖。生成结果关联匹配任务与选择对象，资料版本变化会阻止覆盖旧文案。
- 独立草稿页面移除；邮箱设置位于账号设置；邮件详情只保留固定返回按钮，预览关闭为右上角 X。
- MinIO 使用官方源码版本 7aac2a2c5b7c 本地构建。381 份现有文件共 50,990,079 字节迁移并回读校验；原生上传 204、完成 201，S3 中字节一致，旧附件经原鉴权接口下载 200 且摘要一致。
- 合成职业资料已通过当前模型真实生成沟通文案，未创建业务记录、未外发。

最终回归：前端 73 项、服务端 205 项、ops 25 项通过（共 303 项），类型与 lint 通过。页面核对了统一队列类型过滤、手动匹配原地完成、邮箱设置实际入口、邮件固定返回以及 S3 附件预览。没有自动联系、发送或发布。


## 取消本地 MinIO

按用户要求恢复 Twenty 本地磁盘驱动，保留官方文件服务及 S3 驱动能力。桶内 383 个对象共 50,990,171 字节已逐个备份、写回原路径并核对 SHA256，包括切换后新增的文件。移除 MinIO 专属构建、容器配置和启动钩子；业务附件接口不变。
