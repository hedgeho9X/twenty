## 4. 公司与 JD 的统一入口

### 4.1 先调查真实字段与原始材料

- 盘点 company、recruitmentJob、intake 的对象、字段、关系、实际填充率和来源形状。
- 区分原始输入、公司补充、岗位偏好、派生 JSON、人工运营信息，不能凭派生字段反推并伪造原件。
- 当前只读基线：53 公司、166 未删除岗位；163 岗有关联公司，163 有 JD，139 有岗位偏好，100 有公司偏好快照；完整性须在迁移时再核对。
- 对旧输入无法重建的部分保留来源和缺失状态，不把历史结构化 JSON 当原始 JD。

### 4.2 实习生交互

1. 在“公司与岗位”入口搜索并选择公司，显示名称、域名及已有岗位避免选错。
2. 找不到时就地新建公司，填写基础信息和可选简介，不丢失待上传材料。
3. 选定公司后，粘贴文字或上传一个/多个 JD 文件，可填写可选补充说明。
4. 展示待创建岗位预览列表：公司、名称、来源、识别字段、缺失项和重复提示；允许逐行修正、删除和确认。
5. 批量提交返回 batchId 和各 itemId；每项独立状态、错误、重试和记录链接，失败项不影响成功项。

### 4.3 统一服务

- 公司查找/新建、JD 材料提交、预览/确认、批量创建与进度均有鉴权接口。
- 对确切外部 ID 使用幂等键；名称近似只给重复提示，不能自动合并不同公司或不同岗位。
- JD、岗位专属偏好、公司简介及招聘偏好分别保存和版本化；人工修订不能被重试覆盖。
- 公司上下文修改会使相关匹配结果过期并安排增量重评。

## 5. 候选人材料入口与整理

- 手动页面、API、邮件使用同一接收服务；原件、可选 `note`、来源标识、提交者与时间完整保存。
- 提交记录与候选人记录分开。HTTP 202 只表示已持久化并排队，不表示解析、建人或匹配成功。
- 支持图片、PDF、DOCX、旧 DOC、TXT、HTML、Markdown；旧 DOC 单独验证。其他已有附件格式保留原件并明确自动解析能力。
- Docling 为解析基线。使用真实样例验证中文、两栏、扫描、表格、损坏文件和长材料，不宣称未经测试的“最优”。
- PDF 每页截图；Word 固定渲染为 PDF 后逐页截图；HTML/Markdown 隔离渲染、长页面完整分段截图；图片使用原图。
- HTML/Markdown 禁止执行脚本及任意外网/本地访问；缺资源需报告。长材料不可静默截断或丢页，记录完整覆盖情况。
- 模型输入包含解析文字、原始说明和必要页图，复用官方 Provider/AI SDK；不再启动旧 Codex CLI/Python Agent 执行材料任务。
- 一次结构化生成输出基础资料、职业事实、skills、summary、明确的本次 `expectedRoles`、可空 enum `category`、可核查的求职条件；不沿用旧复杂证据 JSON。
- 不把历史任职当当前意向，不把顾问推测当候选人原话；冲突保留供确认，未知保持未知。
- ResumeIngestJob 并发上限 10，共享解析资源。持久业务状态独立于 Redis job 清理；失败可重试，幂等防重复建人和重复模型消耗。
- 成功写入/关联 Twenty 候选人列表，提供记录跳转链接。身份合并不能只按姓名；匹配失败不撤销已入库候选人。

## 6. 邮件完整接入

- 核实既有 Twenty IMAP 同步与邮件事件，再连接统一材料入口，不另建材料解析链。
- 保存完整 RFC822/EML、Message-ID、文件夹/UID、收发件人、主题、时间、text/html、全部附件及内嵌资源。
- 区分简历附件、签名图片及其他资料，但都归档；正文说明可作为 note，系统来源信息单独保存。
- 事件与业务提交双层幂等；重复事件、断线与重试不得重复建候选人或反复评分。
- 优先用合成邮件验证；受控实收不批量重放历史、不发送邮件。新环境不得自动启动旧生产工作流或对外副作用。

## 7. 双向匹配 Pipeline

### 7.1 当前默认方案

- 当前规模采用“候选人完整相关职业资料 + 一个岗位 + 有用公司上下文”的 1:1 Jev 评估，再排序。
- 候选人匹配岗位和岗位匹配候选人共用同一个 PairEvaluator、输入构造器和缓存；改变排序视角不能改变同一人岗对的分数。
- 不把所有岗位一次塞进模型。Embedding 保留作对照和未来扩容召回层，当前不是必经的前置过滤。
- 先由程序过滤明确不可投条件：停招、明确不接受的雇佣类型等；未知进入待确认，不根据资深、年龄等推断偏好。
- category 辅助展示和检索，不做漏掉跨方向候选人的强制前提。
- 上下文包括相关职业事实、当前意向和条件、完整 JD、岗位偏好、公司简介与公司招聘偏好；不夹带无关联系方式和重复内容。
- 按实际 Jev 模型/协议核对窗口并计量输入；超限明确分解或待处理，不静默删文本。豆包 token 数不能当 Jev 精确计数。

### 7.2 打分与展示

- Jev 是 TypeSafe 的结构化决策模型；`match-v0.1` 才是旧实验的评分协议。不得混称 Jev 为本地提示词或默认等同某种未披露网络架构。
- 能力匹配、求职意向、条件冲突和资料不足分开表示，不能把硬冲突与高能力分求平均。
- 优先保留已实测能力分作为基线，其他问题和规则作为新协议候选，通过评测后选择，不未经验证就把提议当成功方案。
- 展示最多前五，允许不足五个或无合适结果；区分相对排名、待确认、可沟通建议及最终人工推荐。
- Jev 不生成自由文本理由，不虚构其解释、维度分或证据。程序过滤原因可直接展示；另行生成的说明须标明来源。
- 同公司重复/近重复岗位先识别，明确记录去重依据，不随意删掉地点/级别不同的真实岗位。
- 每对独立状态、可恢复失败和有限重试；失败不是 0 分。部分结果标明成功覆盖量，不冒充全量排名。
- 缓存至少包含候选人版本、岗位版本、公司上下文版本、模型标识、协议版本；更新后只重算受影响的组合。

## 8. 可快速迭代的评测体系

- 建立数据准备 → 固定样本 → 执行 Pipeline → 独立审阅 → 差异定位 → 单项变更 → 回归报告的实验命令与可视化结果。
- 复用实验会话已有 30 人、46 在招岗位、1,380 对真实 Jev 结果、向量缓存和材料复核，避免无意义重跑。
- 旧 Embedding 前五的 150 项审阅是 Agent 初审，不能宣称为用户确认的 gold labels；Jev 新前五仍需独立复核。
- 覆盖技术、产品、运营、设计、无明确意向、缺资料、明确不接受实习、否定约束、职责相近但不同、重复岗位、输入被误删等情况。
- 候选人分组划分调优集与保留测试集；同一候选人/重复岗位不能跨集合泄漏，不能对测试集反复调参后再报告未见样本效果。
- 分别报告硬约束违规、未知被误拒、输入保真、重复占位、前五可沟通率、排序一致性、模型调用覆盖、费用和延迟；不把与 Agent 判断一致当客观正确。
- 保留人/Agent 初审与 Jev 不一致的具体材料、规则、概率及版本，分析是输入、规则、评分协议还是标签问题。
- 每轮冻结输入、模型/网关实际标识、协议、代码 commit、运行时间、并发、重试、用量和结果。变更有界，不无限调优或无限花费。
- 先复用缓存跑离线回归，再做必要的真实小批验证。费用与调用量写入证据，不把接口成功当业务质量通过。

## 9. Agent 可调用能力

- 先调查官方能力：REST `/rest`、GraphQL `/graphql`、元数据、官方 `/mcp` 和 CLI；复用鉴权与角色，不另造万能管理员 Token。
- 统一招聘领域服务对 UI、HTTP、MCP、CLI 暴露相同行为，不能让 Agent 绕过排队、幂等、校验和人工确认。
- 至少支持：公司搜索与创建、批量 JD 提交/确认、简历提交、查看处理进度、候选人匹配岗位、岗位匹配候选人、指定人岗手动匹配、获取结果和来源记录链接、生成/获取问候草稿及记录人工跟进。
- 长任务返回任务 ID，提供分页查询/状态/失败重试；不能要求 MCP 调用一直阻塞到模型完成。
- 原生工具可承载时注册到官方 Tool Registry/MCP；文件传输不能假设远程 Agent 能读取服务器本地路径，设计上传授权/文件 ID 路径。
- 官方 CLI 不足之处只补薄封装，输出稳定 JSON、退出码与任务等待选项；skill 描述顺序、输入示例、错误恢复和人工动作边界。
- 验收用有权限的 Agent 完成“查公司 → 建 JD → 上传简历 → 等处理 → 双向/指定匹配 → 取结果”，并验证越权、失效凭据和重复请求。

## 12. 工作顺序与完成标准

执行顺序可因依赖并行推进，但不使用子 Agent，除非用户另行要求或适用指令明确要求。

1. 冻结目标、核实官方 API/UI/订阅扩展点，记录字段与数据迁移映射。
2. 启动官方源码本地底座，建立独立环境与可回读的数据迁移。
3. 实现公司/JD 与简历统一接收、批量预览确认、归档与队列状态。
4. 接解析截图、官方模型生成与候选人/JD 写入。
5. 实现共享逐对匹配、明确约束、缓存、双向排序、评测回归。
6. 接官方 MCP/CLI 和技能，跑完整 Agent 操作场景。
7. 完成运营页面、草稿、人工跟进与门户保留能力，接受控邮件输入。
8. 完成订阅进程内集成与可授权部分验证，整体回归、文档和交付。
